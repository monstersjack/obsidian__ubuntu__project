### 一、三个对象分别负责什么

| 对象                                               | 负责的事情                                                           | 不负责的事情                              |
| ------------------------------------------------ | --------------------------------------------------------------- | ----------------------------------- |
| `sudo systemctl start xline-ws3-runtime.service` | 启动整套 ROS 2 硬件运行栈，包括轮驱、IMU、全站仪驱动、喷墨、定位、路径规划、基础控制器和 `cmd_vel_mux` | 不代表传感器已经有效；不代表定位已经校准；不会自动授权小车运动     |
| `/emergency_stop`                                | 接收 `true` 后立即让仲裁器进入“锁存停车”，清除速度来源并持续输出零速                         | 发布 `false` 不会解除锁存；不能代替实体急停          |
| `/emergency_stop/reset`                          | 在冲突和非零速度来源都消失后，人工解除软件急停锁存                                       | 不会恢复旧速度；不会直接让小车行走；不能修复 IMU、全站仪或定位故障 |

三者的关系如下：

```mermaid
flowchart TD
    A[systemctl start<br/>启动整套 ROS 运行栈] --> B[cmd_vel_mux 启动]
    B --> C[启动默认锁存停车]
    C --> D{图结构正常且上游无非零速度?}
    D -- 否 --> E[拒绝 reset<br/>继续发布零速]
    D -- 是 --> F[调用 /emergency_stop/reset]
    F --> G[约 0.6 秒复位冷却]
    G --> H[所用输入源发送零速握手]
    H --> I[允许新的速度会话]
    I --> J[/task_cmd_vel 或 /tablet_cmd_vel]
    J --> K[唯一 cmd_vel_mux]
    K --> L[/cmd_vel]
    L --> M[轮驱 CAN]
    N[/emergency_stop = true] --> C
```

### 二、`sudo systemctl start xline-ws3-runtime.service` 的准确含义

这条命令通过 systemd 启动 `/home/qingz/xline_app_backend1/run_ws3_runtime.sh`。服务单元由 root 管理，但其 ROS 进程配置为以用户 `qingz`、组 `qingz` 运行。

当前环境配置使运行脚本进入全站仪硬件分支，实际执行：

```bash
ros2 launch xline_bringup system_test.launch.py \
  enable_hardware:=true enable_foxglove:=false
```

从用户提供的 `systemctl status` 可以确认，它启动了下列主要节点：

| 进程或节点 | 作用 |
|---|---|
| `differential_wheels_driver` | 接收最终 `/cmd_vel`，控制左右轮 CAN |
| `beiwei_imu_driver_node` | 读取 IMU |
| `ln150_driver` | 全站仪 LN150 驱动 |
| `inkjet_printer_node` | 喷墨控制 |
| `cmd_vel_mux` | 速度仲裁并唯一发布 `/cmd_vel` |
| `localization` | 融合定位并发布有效位姿 |
| `path_planner` | 路径规划 |
| `base_controller` | 路径跟踪并向 `/task_cmd_vel` 输出任务速度 |

#### `start`、`enable`、`active`、`disabled` 的区别

| 状态或命令 | 含义 |
|---|---|
| `sudo systemctl start ...` | 只启动本次运行，不改变下次开机策略 |
| `systemctl is-active ...` 返回 `active` | 当前服务正在运行 |
| `Loaded: ... disabled` | 当前没有设置为开机自动启动；与“此刻正在运行”不冲突 |
| `vendor preset: enabled` | 软件包或系统的建议预设是启用，不等于本机当前已经 `enable` |
| `sudo systemctl enable ...` | 设置以后开机自动启动，但不会立即启动，除非加 `--now` |
| `sudo systemctl enable --now ...` | 同时设置开机自启并立即启动 |
| `sudo systemctl stop ...` | 停止整套 ROS 运行栈；停止后 `/cmd_vel` 通常会变成不存在 |
| `sudo systemctl restart ...` | 停止后重新启动；新的仲裁器仍会重新进入启动锁存 |

因此，日志中的 `Active: active (running)` 和 `Loaded: ... disabled` 同时出现是正常的：服务已经被手动启动，但没有设置为下次开机自动启动。

### 三、为什么启动前显示 `Unknown topic '/cmd_vel'`

启动前的输出是：

```text
inactive
Unknown topic '/cmd_vel'
```

这与当时的 ROS 图完全一致：

1. `xline-ws3-runtime.service` 尚未运行；
2. `/cmd_vel_mux` 节点不存在；
3. 没有节点创建 `/cmd_vel` 发布者或订阅者；
4. 因此 `ros2 topic info /cmd_vel -v` 报 `Unknown topic`。

这不是 `/cmd_vel` 自身损坏。启动服务后应重新执行：

```bash
systemctl is-active xline-ws3-runtime.service
ros2 node list | grep -x /cmd_vel_mux
ros2 topic info /cmd_vel -v
```

合格结果必须是：

| 检查项 | 合格条件 |
|---|---|
| 运行服务 | `active` |
| 仲裁节点 | 恰好能找到 `/cmd_vel_mux` |
| `/cmd_vel` 发布者 | `Publisher count: 1` |
| 唯一发布节点 | `Node name: cmd_vel_mux` |
| `/cmd_vel` 订阅者 | 包含 `differential_wheels_driver` |

若发布者不是 1 个，禁止发运动命令。`ros2 node list` 只能辅助确认节点存在，最终必须用 `ros2 topic info /cmd_vel -v` 检查真正的发布者数量。

### 四、`/emergency_stop` 软件急停的执行逻辑

软件急停话题类型是：

```bash
ros2 topic type /emergency_stop
```

预期返回：

```text
std_msgs/msg/Bool
```

触发软件急停：

```bash
ros2 topic pub --once /emergency_stop std_msgs/msg/Bool '{data: true}'
```

仲裁器收到 `true` 后按源码执行：

1. 记录最近一次急停时间；
2. 把 `emergency_stop_latched` 设为 `true`；
3. 清除 `/task_cmd_vel` 和 `/tablet_cmd_vel` 的旧来源租约与缓存命令；
4. 将拒绝原因设为软件急停锁存；
5. 向 `/cmd_vel` 发布零速；
6. 后续看门狗周期继续保持停车；
7. 在人工调用复位服务之前，拒绝新的非零速度。

#### 为什么发布 `false` 不能复位

下面的命令**不能解除锁存**：

```bash
ros2 topic pub --once /emergency_stop std_msgs/msg/Bool '{data: false}'
```

源码明确规定：`false` 不是运动授权。当仲裁器已经锁存时，收到 `false` 仍继续发布零速。这样可避免急停发送程序重启、话题默认值变为 `false` 或通信抖动时，小车意外恢复旧运动。

#### 软件急停与实体急停的区别

| 软件急停 | 实体急停 |
|---|---|
| 依赖 ROS、操作系统、网络和仲裁器仍能运行 | 独立硬件安全链路，不应依赖 ROS |
| 用于程序级锁存停车和测试保护 | 人员、机械或运动失控时优先使用 |
| 不能代替物理断能 | 是现场安全的最终保护手段 |

如果小车已经出现危险运动，应先按实体急停，不应等待 SSH 或 ROS 命令执行。

### 五、`/emergency_stop/reset` 复位服务的执行逻辑

查看服务类型：

```bash
ros2 service type /emergency_stop/reset
```

预期返回：

```text
std_srvs/srv/Trigger
```

调用复位：

```bash
ros2 service call /emergency_stop/reset std_srvs/srv/Trigger '{}'
```

复位不是“强制开车”，而是一次带条件的重新授权。仲裁器会先检查：

| 复位前检查                                    | 不合格时的结果         |
| ---------------------------------------- | --------------- |
| `/cmd_vel` 是否仍由唯一的本仲裁器发布                 | 拒绝复位并继续锁存零速     |
| `/cmd_vel_mux/status` 的发布结构是否正常          | 拒绝复位            |
| 最近约 `0.6 s` 内 `/task_cmd_vel` 是否出现非零速度   | 拒绝复位，提示先取消旧任务   |
| 最近约 `0.6 s` 内 `/tablet_cmd_vel` 是否出现非零速度 | 拒绝复位，提示先停止遥控    |
| 最近约 `0.6 s` 内是否仍收到急停 `true`              | 拒绝复位，提示排除持续急停来源 |

复位成功后，仲裁器会：

1. 再次清除所有旧速度来源；
2. 把软件急停锁存设为 `false`；
3. 增加 `reset_generation`，标记这是一个全新的控制会话；
4. 进入约 `0.6 s` 的冷却期，期间持续零速；
5. 要求 `/task_cmd_vel` 和 `/tablet_cmd_vel` 分别重新完成零速握手；
6. 不恢复复位前的任何旧非零速度。

成功响应类似：

```text
success: true
message: 已复位并保持零速；等待0.60秒，再用来源零速握手开始新会话
```

#### 读取仲裁器详细状态

```bash
ros2 service call /cmd_vel_mux/get_status std_srvs/srv/Trigger '{}'
```

重点查看：

| 字段 | 含义 |
|---|---|
| `emergency_stop_latched` | `true` 表示仍锁存停车；`false` 才表示软件锁存已解除 |
| `reason_code` | 当前停车、拒绝或运行状态的机器可读原因 |
| `reason` | 中文原因说明 |
| `resume_wait_s` | 复位后剩余冷却时间 |
| `source_requires_zero.task` | 任务输入是否仍需零速握手 |
| `source_requires_zero.tablet` | 网页人工输入是否仍需零速握手 |
| `zero_ack_seq` | 各输入源已确认的零速握手序号 |
| `source` | 当前被仲裁器选中的速度来源 |
| `output` | 仲裁器当前发布的最终速度 |

### 六、从启动到允许任务运动的正确顺序

#### 第 1 步：设置每个终端的 ROS 环境

```bash
cd /home/qingz/xline_ws4/xline_ws3
source /opt/ros/humble/setup.bash
source /home/qingz/xline_ws4/xline_ws3/install/setup.bash
export ROS_LOCALHOST_ONLY=1
export ROS_DOMAIN_ID=0
```

systemd 服务会读取自己的 ROS 环境；上面四条命令是让当前交互终端进入同一个 ROS 域。新开一个终端后必须重新执行。

#### 第 2 步：先查服务和旧发布者

```bash
systemctl is-active xline-ws3-runtime.service
ros2 topic info /cmd_vel -v
```

如果服务已经是 `active`，不要再次手动启动 `cmd_vel_mux`。如果服务未运行且 `/cmd_vel` 不存在，才执行下一步。

#### 第 3 步：启动整套运行服务

```bash
sudo systemctl start xline-ws3-runtime.service
systemctl is-active xline-ws3-runtime.service
systemctl status xline-ws3-runtime.service --no-pager -l
```

#### 第 4 步：确认最终速度发布者唯一

```bash
ros2 node list | grep -x /cmd_vel_mux
ros2 topic info /cmd_vel -v
ros2 topic info /cmd_vel_mux/status -v
```

只有 `/cmd_vel` 的 `Publisher count: 1` 且唯一节点为 `cmd_vel_mux` 时才能继续。

#### 第 5 步：确认没有旧上游速度

```bash
ros2 topic info /task_cmd_vel -v
ros2 topic info /tablet_cmd_vel -v
ros2 service call /cmd_vel_mux/get_status std_srvs/srv/Trigger '{}'
```

先停止旧 CAD Action、旧测试发布器和网页遥控。不要通过直接发布 `/cmd_vel` 来绕过仲裁器。

#### 第 6 步：人工复位软件急停

```bash
ros2 service call /emergency_stop/reset std_srvs/srv/Trigger '{}'
sleep 1
ros2 service call /cmd_vel_mux/get_status std_srvs/srv/Trigger '{}'
```

若返回 `success: false`，阅读 `message` 并排除原因，不要连续反复调用复位。

#### 第 7 步：对将要使用的来源执行零速握手

CAD 划线和自动任务使用 `/task_cmd_vel`：

```bash
ros2 topic pub --times 5 --rate 10 /task_cmd_vel geometry_msgs/msg/Twist \
  '{linear: {x: 0.0}, angular: {z: 0.0}}'
```

8080 网页人工控制使用 `/tablet_cmd_vel`。正常情况下由网页后端自己完成握手；人工诊断时可执行：

```bash
ros2 topic pub --times 5 --rate 10 /tablet_cmd_vel geometry_msgs/msg/Twist \
  '{linear: {x: 0.0}, angular: {z: 0.0}}'
```

随后再次查询状态：

```bash
ros2 service call /cmd_vel_mux/get_status std_srvs/srv/Trigger '{}'
ros2 topic echo /cmd_vel --once
```

最终 `/cmd_vel` 仍应为零；所用来源对应的 `source_requires_zero` 应变为 `false`。

### 七、用户提供的 `systemctl status` 逐项解释

| 输出 | 解释 |
|---|---|
| `Loaded: loaded` | systemd 已找到并加载服务单元 |
| `disabled` | 没有设置开机自动启动，不代表当前停止 |
| `vendor preset: enabled` | 系统预设建议启用，但本机当前仍是 disabled |
| `Active: active (running)` | 服务当前正在运行 |

状态中列出的 `cmd_vel_mux_node` 证明仲裁器进程已经启动，但仍需使用下面的命令证明它是 `/cmd_vel` 的唯一发布者：

```bash

```

### 八、定位和 IMU 日志该如何理解

用户日志中出现：

```text
定位无效：未校准或 IMU/反射板超时；不会发布伪造的零位姿
定位尚未校准或 IMU 不新鲜；停止发布位姿
IMU 零偏校正完成
Init OK!
IMU Performance: 0.0 Hz (target: 200Hz)
```

这些信息说明：

| 日志 | 准确含义 |
|---|---|
| `IMU 零偏校正完成`、`Init OK!` | IMU 驱动初始化流程已走到成功阶段 |
| `0.0 Hz (target: 200Hz)` | 当时性能统计窗口尚未收到有效 IMU 数据，或数据流仍未建立；不能仅凭 `Init OK` 判断 IMU 已健康 |
| `定位无效` | 定位节点主动拒绝发布伪造零位姿，这是保护行为 |
| `未校准或 IMU/反射板超时` | `/robot_pose` 等有效定位条件尚未满足，可能还缺定位校准、IMU 新鲜数据或全站仪反射板数据 |

因此：

```text
systemd 服务 active
≠ 每个传感器有效
≠ 定位已校准
≠ CAD 划线可以立即开始
≠ 小车已经获得运动授权
```

速度仲裁器是否在线与定位是否有效是两条不同的检查链。低层人工速度链路可以单独诊断，但 CAD 精准划线必须在 IMU、反射板、定位校准和 `/robot_pose` 全部有效后才能开始。

### 九、停止、重新启动与急停的选择

| 需求 | 正确操作 |
|---|---|
| 程序正常运行，但需要软件锁存停车 | 发布 `/emergency_stop = true` |
| 已排除风险，需要建立新的控制会话 | 调用 `/emergency_stop/reset`，等待冷却并执行零速握手 |
| 需要结束整套 ROS 硬件运行栈 | 先确认小车已停，再 `sudo systemctl stop xline-ws3-runtime.service` |
| 修改配置或重新加载整套运行栈 | 先停车，再 `sudo systemctl restart xline-ws3-runtime.service`；重启后重新复位与握手 |
| 发生人员或机械危险 | 立即使用实体急停，不等待软件命令 |

停止服务命令：

```bash
sudo systemctl stop xline-ws3-runtime.service
systemctl is-active xline-ws3-runtime.service
```

停止后返回 `inactive`，并且 `/cmd_vel` 变为 `Unknown topic`，属于正常现象。此时不是“唯一发布者检查通过”，而是整套运行栈根本没有运行。

### 十、常见问题快速判断表

| 现象 | 原因或检查方向 |
|---|---|
| 服务 `inactive`，`/cmd_vel` 为 Unknown topic | 运行栈尚未启动，属于正常对应关系 |
| 服务 `active`，但 `/cmd_vel` 仍不存在 | 启动文件中的仲裁器失败；检查 journal 日志 |
| `/cmd_vel` 有多个发布者 | 存在旧测试节点或第二套仲裁器，禁止运动并停止冲突源 |
| reset 返回“上游仍在发布非零速度” | 旧任务或网页仍在刷新速度；先终止上游发布器 |
| reset 返回“最近仍收到急停 true” | 某个程序持续发布急停；停止该来源，等待超过约 0.6 s 后再复位 |
| reset 成功但仍不能走 | 仍处于冷却期，或尚未对所用来源完成零速握手 |
| 发布 `/emergency_stop false` 后仍不能走 | 设计如此；必须调用 Trigger 复位服务 |
| 仲裁器正常但 CAD 不能划线 | 继续检查 IMU、全站仪、定位校准、`/robot_pose` 和 Action，不要绕过定位保护 |

查看最近服务日志：

```bash
journalctl -u xline-ws3-runtime.service -n 100 --no-pager
```

持续查看日志：

```bash
journalctl -u xline-ws3-runtime.service -f
```

### 十一、推荐的只读验收命令组

以下命令不会主动发布运动速度，可用于每次启动后的验收：

```bash
systemctl is-active xline-ws3-runtime.service
ros2 node list | grep -E '^/(cmd_vel_mux|differential_wheels_driver|localization)$'
ros2 topic info /cmd_vel -v
ros2 topic info /cmd_vel_mux/status -v
ros2 topic info /task_cmd_vel -v
ros2 topic info /tablet_cmd_vel -v
ros2 service list | grep -E '^/(cmd_vel_mux/get_status|emergency_stop/reset)$'
ros2 service call /cmd_vel_mux/get_status std_srvs/srv/Trigger '{}'
ros2 topic echo /cmd_vel --once
```

最终判断不能只看“服务 active”，而应同时满足：

1. `/cmd_vel` 只有一个发布者，并且是 `cmd_vel_mux`；
2. 轮驱订阅 `/cmd_vel`；
3. 软件急停状态符合当前操作阶段；
4. 当前输出为零，旧速度来源已经清除；
5. 若要执行 CAD 划线，IMU、全站仪、定位校准和有效位姿也全部就绪。
